# SoulMirror 3.0 设计方案（生产级 · 可离线 · 无需会议软件即可验证）

> 相对 2.0 的三处根本变化：
> 1. **取消说话人识别**（不做 diarization）
> 2. **ASR 换成 DSH 内置的 SenseVoice**（本地、离线、批处理接口）
> 3. **整个系统可在没有会议软件的情况下端到端验证**

---

## 0. 一个必须先讲清楚的事实：DSH 的 ASR 是批处理，不是流式

我查了 DSH 实际注册的服务与实现：

```
服务：speechToText（Host）
接口：resolve({ audio: Uint8Array, language? }) → transcribe(spec, signal) → Transcript
返回：{ text, audioSeconds, inferenceSeconds }
```

`audio` 是**整段 WAV 字节**，返回**整段文本**。没有 partial、没有时间戳、没有说话人。

内置 provider：

| 项 | 值 |
|---|---|
| 实现 | SenseVoiceSmall ONNX + Silero VAD |
| 运行时 | `sherpa-onnx-node`（自带 ONNX Runtime，无需 Python/编译器） |
| int8 模型 | **239,233,841 B ≈ 228 MB** |
| fp32 模型 | 894 MB |
| 词表 | 316 KB |
| VAD | Silero 1.8 MB |
| 语言 | 中/英/日/韩/粤 |
| 执行方式 | 宿主 Node 子进程，**串行**推理，有界队列 |
| 可调 | `threads` / `segmentSeconds` / `vadThreshold` / `minSpeechSeconds` / `minSilenceSeconds` / `maxPending` / `idleTimeoutMs` |
| 下载 | 首次需下载（支持 huggingface.co / hf-mirror.com 双源，SHA-256 校验） |
| 本机现状 | **模型尚未下载**（voice input 从未用过） |

**这意味着**：想要"实时"，我们必须自己造一个**分段器**，把批处理接口伪装成流式。这是本方案的核心工程点，也是最大的风险点。

### 与云端流式的取舍

| 维度 | DashScope 实时（旧） | DSH SenseVoice（新） |
|---|---|---|
| 延迟 | 1–3 s（真流式） | **≈ 段长 + 0.3–0.8 s** |
| 成本 | 按小时计费 | **0 元**（只花 CPU） |
| 离线 | 不行 | **可以** |
| 隐私 | 音频出云 | **不出本机** |
| 说话人 | 无 | 无 |
| 时间戳 | 有 | 无 |
| 首次部署 | 只需 key | **下载 228 MB** |

结论：用本地换"零成本 + 离线 + 隐私"，代价是**延迟从秒级变成"段级"**。方案按 3 秒分段，端到端约 3.5–4 秒。

## 1. 目标与非目标

### 目标

1. 实时转写（无说话人），端到端 P50 ≤ 4 s
2. 自动检测会议软件 + 捕获会议号
3. 通过对话创建/加入会议
4. 可开关的 Agent 自动化（判断"在对我说话"→ 执行 → 回复）
5. 会后自动归档
6. 与 DSH 原生一致的 UI/UX
7. **不安装任何会议软件也能完整验证**（开发测试 + 用户演练）

### 非目标

- 说话人识别/分离（已明确取消）
- 视频处理
- 跨平台（Windows 优先，接口预留）

## 2. 架构：四层接口 + 双实现

**可测性的根本做法是把"外部世界"抽象成接口，每个接口都有真实实现和模拟实现。**

```
┌──────────────────────────────────────────────────────────┐
│ 编排层  meeting-core（状态机，纯逻辑，不碰 IO）             │
└──────┬───────────────┬──────────────┬───────────────────┘
       │               │              │
┌──────▼─────┐ ┌───────▼──────┐ ┌─────▼──────────┐
│SignalSource│ │ AudioSource  │ │  Transcriber   │
├────────────┤ ├──────────────┤ ├────────────────┤
│ Desktop    │ │ Loopback     │ │ DshSpeech      │
│ Scripted ★ │ │ WavFile   ★  │ │ Fake       ★   │
└────────────┘ └──────────────┘ └────────────────┘
        ★ = 测试/演练用，无需任何会议软件
```

```ts
interface SignalSource {
  poll(): Promise<MeetingSignal>   // { app, title, code, inMeeting, micHeld }
  dispose(): void
}

interface AudioSource {
  start(): Promise<void>
  chunks(): AsyncIterable<Uint8Array>  // 16k mono PCM16
  health(): { bytes: number, silentMs: number, lastChunkAt: number }
  stop(): Promise<void>
}

interface Transcriber {
  transcribe(wav: Uint8Array, opts: { language: string }): Promise<{ text, ms, audioSeconds }>
}
```

**收益**：状态机、分段器、Agent 判定、归档全部可以脱离桌面和真实音频测试。

## 3. 转写子系统（本方案最核心的部分）

### 3.1 分段器（Segmenter）

输入连续 PCM，输出"可提交的 WAV 段"。策略三选一（按优先级）：

```
1. 静音切分：连续静音 ≥ 700ms → 立即切（最自然，延迟最低）
2. 长度上限：累计 ≥ 3s（可配 2–8s）→ 强制切（防长句不落）
3. 兜底：累计 ≥ 8s 且仍在说话 → 硬切（防无限增长）
```

每段结构：

```ts
{ seq: number, startMs: number, endMs: number, wav: Uint8Array }
```

**为什么不用 provider 内部的 `segmentSeconds`**：它返回一整段文本且无时间戳，我们要自己控制节奏和延迟，所以上位控制权必须在我们手里。

### 3.2 并发与背压

provider 是**串行子进程**，有 `maxPending`：

```
提交并发 = 1（单通道，天然不乱序）
队列上限 = 3 段
溢出策略 = 丢弃最旧的一段并记事件（宁可丢一句，不可让队列无限涨）
```

推理耗时预期：SenseVoiceSmall int8，4 线程，3 秒音频约 0.3–0.8 秒（RTF ≈ 0.1–0.25）。3 秒段 → 占空比 ≤ 30%，一小时会议 CPU 占用可接受。

> 这条必须在实现的第一天用真实模型实测并写进验收，不能靠估算。

### 3.3 拼接与去重

段与段之间允许 150–250 ms 重叠（提高边界词准确率），因此必须去重：

```
1. 文本级：找「上一段结尾」与「本段开头」的最长公共子串（≥ 4 字）→ 裁掉
2. 时间级：重叠区间内的词只保留一次（无时间戳，故以文本为准）
3. 空段：text 为空 → 丢弃，不产生占位行
```

### 3.4 延迟预算（写进验收）

| 环节 | 预算 |
|---|---|
| 分段等待（静音触发） | P50 0.7 s |
| 分段等待（长度触发） | 3.0 s |
| provider 推理 | 0.3–0.8 s |
| 落库 + UI 推送 | ≤ 100 ms |
| **端到端 P50** | **≤ 4 s** |
| **端到端 P95** | **≤ 7 s** |

### 3.5 失败与恢复

| 故障 | 检测 | 处理 |
|---|---|---|
| provider 未准备（模型没下载） | `snapshot()` phase ≠ ready | 触发 `prepare()`，UI 显示下载进度（字节数） |
| worker 崩溃 | transcribe 抛错 / 超时 | 该段重试 1 次，失败则该段标记 `failed`，继续下一段（不阻塞流水） |
| 推理超时 | 单段 > 10 s | 取消 + 记事件 + 降低后续段长 |
| 队列溢出 | pending > 3 | 丢最旧 + 事件 + 指标自增 |
| 模型校验失败 | 启动检查 | 明确提示"模型损坏，需重新下载"，不静默 |

## 4. 会议检测与会议号

### 4.1 检测（5 s 轮询，仅总开关开启时）

```
进程白名单 → 窗口类名/标题 → 评分（腾讯会议 100 / 移动会议 90 / 飞书 80 / 钉钉 70 / Zoom 60 / Teams 55）
低于 60 → 视为未开会
```

**"在会中"三信号任一命中**：会中窗口类名 / 标题≠软件名 / 该进程占用麦克风（`state=1`）。

### 4.2 会议号（按可信度降序，命中即停）

| 序 | 来源 | 例 |
|---|---|---|
| 1 | 会议内文本控件 | `983 593 253` |
| 2 | 带标签文本 | `移动会议：379422987` |
| 3 | 邀请链接 | `…/share/379422987` |
| 4 | 裸号（三位分组 / 9–11 位，排除 19xx/20xx） | `983593253` |

全部未命中 → 显示"未识别（该客户端不暴露会议号）"，允许手填一次并记住。**不编造。**

## 6. Agent 自动化

### 6.1 开关

```
enabled=false           → 什么都不做（不采集、不轮询、不调模型）
enabled=true, mode=transcribe → 只转写 + 纪要
enabled=true, mode=agent      → 判定 + 执行 + 发言
```

### 6.2 "在对我说话"判定（无说话人依赖）

因为取消了说话人，判定只依赖**文本**：

| 信号 | 权重 |
|---|---|
| 称呼（我的名字/昵称/职位，可配） | 0.40 |
| 疑问/请求句式（帮我/能不能/你看下/是不是） | 0.30 |
| 第二人称（你/您/你们） | 0.10 |
| 上下文（LLM 判定，可选） | 0.20 |

阈值 0.6 触发；同话题冷却 60 s；每分钟判定 ≤ 1 次；每小时发言 ≤ N 次（可配）。

**限制必须写在 UI 上**：没有说话人识别时，多人会议里"谁在说"不可知，判定只看内容——误触发概率随人数上升。这是取消 diarization 的直接代价，不能隐瞒。

### 6.3 执行与发言

```
触发 → 组上下文（最近 20 句 + 人格 + 记忆摘要）
     → 需查资料/执行操作 → 建/复用 DSH 会话
     → 回答 → TTS → 播到虚拟声卡 → 会议麦克风
     → 同时在转写流插一条 role=assistant（UI 可见"我说了什么"）
```

发言安全：用户占麦时延后 2 s 重试（≤3 次）；> 30 s 截断；未配 `devices.speak` 时只本地播放。

## 7. 会后归档

会议结束 → 串行、每步可独立失败：

```
1. 纪要（LLM 归纳；无 key 则抽取式）
2. 写 Markdown（日期 + 会议名 + 会议号 + 时长）
3. 回写知识库（可用时）
4. 待办 → DSH 自动化任务（用户确认后）
5. 制品：transcript.jsonl / minutes.md / events.jsonl
6. 给当前会话发一条汇报（可关）
```

保留策略：文本 90 天、音频 7 天（默认不存音频）。

## 9. 无需会议软件的验证体系（本版新增的关键能力）

### 9.1 四层验证

| 层 | 内容 | 依赖 | 耗时 |
|---|---|---|---|
| L1 单元 | 分段器、去重、会议号解析、状态机、判定打分 | 无 | ms |
| L2 转写 | `WavFileAudio` → 真 SenseVoice → 断言文本 | 需模型（228MB） | 秒 |
| L3 端到端 | `ScriptedSignal` + `WavFileAudio` + `Fake/DshSpeech` → 走完检测→转写→判定→归档 | 无桌面 | 十秒级 |
| L4 演练模式 | 用户可见：内置样例会议音频 + 假会议身份，30 秒看全流程 | 无 | 30 秒 |

### 9.2 演练模式（产品功能，不只是测试）

```
meeting_demo start [--speed 2]
→ SignalSource = ScriptedSignal（"演练 · 983 593 253"，状态在 on/off 间切换）
→ AudioSource = 内置 fixtures/demo_meeting.wav
→ UI 顶部横幅「演练中 · 不连接真实会议 · 不会发言」
→ 结束后照常生成纪要，但不写知识库、不发汇报
```

价值：新用户装机后 30 秒看到效果；售后复现问题不依赖用户装腾讯会议；验收时可演示。

### 9.3 混沌注入

环境变量 `SOULMIRROR_FAULT`：

```
kill-capture   采集进程中途死掉 → 断言自动恢复且不抖
drop-worker    ASR worker 崩溃 → 断言该段失败但流水继续
slow-transcribe 推理变慢 → 断言队列背压与丢最旧
disk-full      写盘失败 → 断言报错可行动，不崩溃
no-model       模型缺失 → 断言引导下载而非静默失败
```

## 10. 生产级工程要求（"不会出 bug"的诚实版本）

我不能承诺零 bug，能承诺的是**不静默失败、可恢复、可诊断**。具体机制：

| 机制 | 做法 |
|---|---|
| 状态机 | 单一所有者、显式 states/events/guards、非法迁移直接抛错 |
| 不变量 | 运行期断言（如"capturing 时只有一个采集进程"），违反即上报 |
| 幂等 | 所有入口可重复调用（start/stop/join/archive） |
| 超时 | 每个外部调用都有超时，无默认无限等待 |
| 熔断 | LLM 连续失败 3 次 → 降级为只转写，并明确告知 |
| 预算 | CPU/内存/磁盘/Token 四类预算，超限降级而非崩溃 |
| 可观测 | `/health`（含延迟 P50/P95、重启次数、队列深度）+ `events.jsonl` |
| 诊断包 | 一键导出最近 24h 事件 + 配置（脱敏），用于报障 |
| 兼容 | 插件版本 + 配置 schema 版本 + 迁移函数 |
| 金丝雀 | 新版本先跑演练模式，再允许接真实会议 |

### 性能与稳定性 SLO（验收基线）

| 指标 | 目标 |
|---|---|
| 端到端转写延迟 P50 / P95 | ≤ 4 s / ≤ 7 s |
| 单场 60 分钟会议采集重启次数 | **0** |
| 崩溃率（异常退出/会话） | 0 |
| 一小时会议 CPU 均值（4 线程） | ≤ 15% |
| 内存峰值 | ≤ 500 MB（含 228MB 模型映射） |
| 首次部署到可用 | ≤ 5 分钟（含模型下载，按 10 Mbps 估） |

## 13. 风险登记

| 风险 | 影响 | 对策 |
|---|---|---|
| SenseVoice 分段延迟高于云端流式 | 观感"没那么实时" | 3 s 段 + 静音优先切；UI 明确显示"正在识别第 N 段" |
| 228 MB 首次下载 | 首次体验差 | 后台下载 + 进度条 + 镜像源 + 未就绪时禁用功能并说明 |
| 批处理无时间戳 | 精确对齐难 | 不追求词级时间戳，只做段级 |
| 无说话人 → 多人误触发 | Agent 乱接话 | 阈值 + 冷却 + 预算 + UI 警示；必要时只对"叫名字"响应 |
| 串行 worker 成为瓶颈 | 长会积压 | 单并发 + 队列上限 3 + 丢最旧 + 指标告警 |
| 移动会议不暴露会议号 | 显示未识别 | 剪贴板/链接兜底 + 手填 |
| HDMI 环回静音 | 采集不到 | 锁定可采设备 + 明确报错；进程环回作为后续根治 |

## 15. 需要你确认的三点

1. **分段长度默认值**：3 s（延迟约 4 s）还是 2 s（延迟约 2.5 s，但短段准确率下降）？我建议 3 s。
2. **模型下载策略**：首次安装即后台下载 228 MB，还是等用户显式开启转写再下载？我建议后者（省流量、`enabled` 语义更干净）。
3. **演练模式是否随插件默认启用**：默认开（新用户能立刻看到效果）还是设置里默认关？

定了我从 M0 开始：先把 Source 抽象和假源端到端骨架做出来——**那一步做完，后面所有功能都能在没有会议软件的环境里验证**。
