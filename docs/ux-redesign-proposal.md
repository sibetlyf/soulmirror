## 0. 评审前提：现有原则（不可违背）

这份设计不提出任何与下列原则冲突的方案。凡与原则冲突的“更漂亮”的做法，都已在第 8.4 节列入“不建议做”。

1. **先落盘后展示**：录音、转写、纪要、知识库写入，都以磁盘/事件日志为准；界面不先宣布成功。
2. **状态只有一份可重建投影**：所有入口（大页面、侧栏、字幕条、状态条）读同一份 `view`；客户端不自己拼运行状态。
3. **不静默回退**：非流式转写失败，不能拿实时草稿冒充纪要；跳过、未入库、抽取摘要都要明说。
4. **无假进度**：进度只来自真实字节/真实事件；`view-model.js:67-72` 已经拒绝用时钟估算百分比，这个边界不能破。
5. **自动检测录音 ≠ 自动入会**：面板可以提示“开会后自动录音”，但不能替用户点入会。
6. **除语音外默认跟随 DSH 会话模型**：模型来源必须可见（绑定会话 / DSH 默认 / 本场快照）。
7. **错误要说清原因与下一步**：错误不是一句“失败”，也不是一屏技术字段。
8. **只用主题 token，且必须带兜底**：任何颜色都写成 `var(--dsw-*, 兜底色)`；否则会重演“主按钮变黑块”的事故。
9. **不引入新依赖**；**不破坏“两个入口共用同一份 view”**。

> 一句话：这次不是“换皮”，是把**状态、层级、动作**重新排一遍，让同一份事实在正确的时刻只出现一次。

## 1. 一页结论：最该先改的 3 条

按“收益 / 成本”排序。每一条都只回答一个问题：**改完用户看到什么不同。**

### P0（先做，成本最低）：把“一个首屏服务所有状态”拆成状态机

让 `view` 明确输出 `mode`（空闲 / 进行中 / 会后 / 历史 / 未配置）和 `meeting`（这场会是谁、多长），主按钮由 `mode` 决定，而不是由“有没有在录音/整理”兜底。

**改完用户看到：** 完成态看到的是“今天 10:42 的会 · 16 分 38 秒 · [看纪要]”；“立即开始录音”只在真的可以开始下一场时出现。

### P1（紧接着，成本低）：诊断收敛成“一个问题 + 一个按钮”，正常状态不再报警

`view.issues` 只保留 error/warn；info 进 `view.notices`；瞬时自动恢复的错误进状态行而不是红条；第一条问题直接给一个动作；字段名只留在“查看原因/复制排查信息”。

**改完用户看到：** 红黄条最多一条，读完知道点哪里；没开会、链路正常时首屏一条告警都没有。

### P2（第二批，成本中等）：卡片五合三，四个平权 tab 改成“2 个入口 + ⋯”

“这场会议”合并产物、纪要、谁在说话、整理进度；“认识的人”合并声纹库与名册；“之前的会议”只留一行入口。设置、诊断、运行轨迹、会议接入全部进 `⋯`。

**改完用户看到：** 一屏只有一块主内容，最多三条折叠行；不用先读完五张卡才知道纪要在哪里。

> 如果只能做一件事：先做 P0 里的“完成态主按钮 + 会议时长”。它只需要改 `lib/view-model.js` 的十几行和 `lib/client.js` 的一处渲染，却能立刻消除“完成了还让我开始录音”的荒诞感。

## 2. 信息架构

### 2.0 参考：其他 DSH 插件怎么组织首屏（只借结构，不搬代码）

| 插件 | 首屏结构 | 值得借用的 | 不照搬的 |
|---|---|---|---|
| `dsh-work-desk`（今日页，`client/today.jsx:305-358`） | 一行量化总结“今天 2 个会，3 条待办，5 封未读” → 一行“下一件/正在进行” → 1 个主按钮 + 2 个次按钮 → 下方分栏卡片；不用装饰性 hero | **首屏用一句话交代全局**；**主按钮只放当前最该做的一件事**；卡片有“标题 + 数量 + 一个动作”，空态用“标题 + 一句解释 + 一个动作”（`today.jsx:69`） | 不做多栏仪表盘（会议面板只有 420px）；不做行情/邮件那种并行的业务块 |
| `dsh-meeting-agent`（`lib/client.js:283-337`） | 380px 侧栏：header 只有“配置 / 关闭”，一行状态标签，四行元信息，一个空态句，footer 只有一个“开始监听/停止监听”主按钮；配置整块切到另一个视图 | **一个状态只配一个动作**；**配置不在首屏**；空态只说“现在该做什么”（等待声音 / 点下方开始监听） | 不把“模型/设备”四行元信息常驻首屏；这些降级到诊断 |
| `dsh-knowledge`（`lib/client.js` 的 `ActivityEmpty`） | 空态是“图标 + 一句结论（这个目录还是空的）+ 一句下一步（可以在完整工作区新建或导入）”，没有堆多个按钮 | **空态先说结论再说下一步**；一个空态最多一个主要出口 | 不引入它的大纲/文档阅读布局；会议面板不需要第二栏 |

三个插件的共同点，恰好是当前会议面板缺的：

1. **首屏回答一个问题，不回答十个问题。** 今日页回答“今天先做什么”，会议监听回答“现在听不听”。会议面板应该回答“这场会进行到哪、下一步点哪里”。
2. **状态与动作绑定。** 一个状态只给一个主按钮，不做“禁用按钮 + 旁边再放三个按钮”。
3. **配置离开首屏。** work-desk 的设置在弹层；meeting-agent 的配置是独立视图；knowledge 的搜索/大纲不挡空态。会议面板也应按这个标准把设置、诊断、轨迹移到 `⋯`。

> 注意：这里只借鉴**入口、首屏、空态、状态呈现**的组织方式；没有复制任何代码、样式或文案。三者的具体业务不同，会议面板的“对象”是一场会，而不是一天或一个知识库。

### 2.2 目标分层：一个对象、一个动作、一条问题

```
L0  全局条（44px）      会议 / 这场会的名字 / 历史 / ⋯
L1  状态与主操作（88px） 现在是什么状态 · 这场会多长 · 唯一主按钮
L2  内容（flex）        转写 / 纪要 / 历史列表（只选一个）
L3  本场折叠行（32-40px × ≤3）  谁在说话 · 产物 · 之前的会议
L4  菜单/抽屉           设置与诊断 · 运行轨迹 · 会议接入 · 导入 · 删除 · 安装
```

四条硬规则：

1. **L1 只能有一个 filled 主按钮。** 其余按钮只能是 outline、text 或图标。
2. **L1 下方最多一条问题。** 多出来的问题折成“还有 N 个问题”，点进 L4，不在首屏堆叠。
3. **L2 不出现配置。** 设备、密钥、模型、安装、依赖全部在 L4；会中不需要它们。
4. **L3 只有“有数据”才出现。** 没录过声纹就不显示“认识的人”；没有历史就不显示“之前的会议”。

### 2.3 导航：2 个入口 + 1 个 ⋯

```
这场会议        历史        ⋯
  │             │          ├─ 设置与诊断
  │             │          ├─ 运行轨迹
  │             │          ├─ 会议接入（会议号 / 打开软件 / 只转录 / 自动回复）
  │             │          ├─ 导入录音
  │             │          └─ 关于 / 帮助
  │             └─ 历史会议列表（默认筛选：有纪要 / 可整理）
  └─ 进行中 = 转写；刚结束 = 纪要；空闲 = 空态
```

- 全局导航只有两个可见项，`⋯` 里的能力一个不少（`client.js:1650` 的四个 tab 能力全部保留，只降级入口）。
- “纪要 / 转写”不再是全局 tab，而是 L2 内容里的局部切换；只有两者都有时才出现。
- 设置与诊断不再与“实时转写”平权。它是一次性配置和故障排查，不该占据每次开会的注意力。

| 层级 | 外观 | 尺寸 | 用在哪 | 数量 |

| 主按钮 | 品牌色填充 + 反白文字 + 图标 | 高 36，宽度随内容（≤260） | 只用于 L1 | 每屏 1 |

1. **禁用的主按钮不渲染。** 整理中显示进度，不显示“后台整理中”的灰按钮。当前 `view-model.js:92` 返回 `disabled: true` 的 primary，界面上仍画出按钮，这是“看起来能点、点了没反应”的典型来源。

3. **主按钮不超过 8 个字，动词开头。** `看纪要`、`结束录音并整理`、`重试这一步`；不用“立即”“点击”“请”。
4. **同一动作不出现两次。** 完成态不再出现“立即开始录音”；纪要已在屏内时，不重复“看纪要”，改为“导出纪要”。
5. **破坏性/低频操作不占首屏。** 删除、导入、安装、重新整理、导出、打开文件夹，全部进 `⋯` 或详情；删除至少两次确认。

### 3.3 明确位置：这些操作放哪

| 操作 | 位置 | 理由 |
|---|---|---|

## 4. 状态与诊断的收敛：一条“问题”，一个“按钮”

### 4.1 现状为什么让人读不懂

- `view.issues` 直接来自 `runtime.issues`（`view-model.js:89`），把 `level` 压成两种：error → error，其余 → warning。于是 `preflight` 的 `info`（“当前没检测到会议窗口”）被涂成黄色警告。
- `client.js:1684` 对每条 issue 直接渲染 `text + fix`，没有“第一条/其余”的区分；`IssueBanner`（1712）里其实已有“第一条 + 全部 N 条 + 复制”的逻辑，但工作台没有用它。
- `issues.js:122-125` 把 `session.lastError` 原样放进 `detail`；`session.js:170 / 308 / 435` 的 lastError 里可能带 `devices.capture`、`devices.captureAuto`。这些字符串会通过 `view.detail`（`view-model.js:62`）出现在最大字号的位置。
- `preflight.js:67 / 247` 的句子把“链路就绪”“没检测到会议窗口”“apps 配置里的进程名”串成一句，用户既不知道这是不是故障，也不知道该点哪。

### 4.2 收敛规则（服务端定，所有入口一致）

1. **分级只有三种，且和呈现一一对应：**
   - `blocker`（error，现在不能录/不能整理）→ 红色，问题行 + 一个动作按钮。
   - `degraded`（warn，能跑但质量受损）→ 黄色，问题行 + 一个动作按钮。
   - `info`（正常上下文/可选功能未开）→ 不进 `issues`，进 `notices`，用灰色一行，不给按钮。
2. **瞬时故障不进告警。** 采集进程退出、ASR 自动重连中，先进 `notices.transient`，显示为状态行；超过 10 秒仍未恢复，才升级成 warn，并给“重新连接”。
3. **同一根因只留一条。** `capture`、`preflight`、`no-transcript`、`asr` 都属于“录音链路”；若 `preflight` 已有致命项，采集错误是症状，不重复报。`issues.js` 已有类似处理（116-126），把它扩展到展示层。
4. **首屏只显示一条。** `topIssue()`（`issues.js:188`）选第一条；其余折成“还有 N 个问题”，点击进 `⋯ → 设置与诊断`，不在首屏展开。
5. **每条问题只有一个动作。** 动作由 `issue.id` 映射，不由用户猜；例如 `key → 填写密钥`、`preflight → 一键体检`、`post-meeting → 重试`。
6. **技术细节下沉。** `detail`、`fix` 里的原始错误放“查看原因”或“复制排查信息”；首屏只留人话。

### 4.3 文案写法规则

- **标题先说“发生了什么”，不先下结论。** “录音中断了”比“采集出错”更像人话。
- **正文只说影响 + 下一步，最多两句。** 每句 ≤22 字；不堆括号。
- **用用户词，不用字段名。** 允许：会议、会议软件、扬声器、耳机、麦克风、录音、转写、纪要、声纹、名字、密钥。禁止出现在首屏：`devices`、`captureAuto`、`apps`、`asr`、`preflight`、`session`、`runtime`、`token`、`401`。
- **数字必须带对象和单位。** “16 分 38 秒”“32 句”“3 位”；不用“998 秒”，也不用“已用 8103 秒”。
- **按钮动词开头。** 主按钮 ≤8 字，其余 ≤6 字；“重新连接”“选设备”“重试这一步”；不用“点击这里”。
- **正常状态不用告警色。** “现在没在开会”是信息，不是问题。
- **技术原因可保留，但放在第二层。** 例如 `查看原因` 里写 `spawn mbridge.exe ENOENT`，首屏只写“音频组件没启动”。

### 5.3 三条减法规则

1. **一块只解决一个问题。** “这场会议”解决“这次开得怎么样”；“认识的人”解决“以后能不能认人”；“之前的会议”解决“上次那份在哪”。
2. **默认只展开一块。** 块 2/3 折叠；用户不点开，它们只占 36px。
3. **同一动作只出现一次。** 声纹安装、导入、重新整理、导出都只在一个地方；不在多个卡片里重复。

## 6. 首次使用引导：从打开页面到第一份纪要，≤5 步

### 6.1 最短路径

| 步 | 用户看到 | 用户动作 | 现有接口 | 现在缺什么 |
|---|---|---|---|---|
| 1 | 状态 D：`3 分钟跑通一次` + 三项体检；密钥缺失时第一项是 ○ | 点 `填写密钥`（环境已提供则显示 ✓ 并跳过） | `GET/POST /api/soulmirror/setup` | 密钥入口埋在设置详情（`client.js:1708`），首屏只有一句“去配置” |
| 2 | 实时转写开始出现（样例音频） | 看 10-20 秒，点 `结束演练` | `POST /api/soulmirror/demo {action:"start"}` / `{action:"stop"}` | 演练入口埋在 `client.js:3007` 的设置页，首屏没有 |
| 3 | `演练转写完成 · 32 句` + `用这段录音生成纪要` | 点生成 | `/demo stop` 后接 `/offline {dir}` | **演练只写 transcript.jsonl，不写 audio.wav，也没接会后整理**（`lib/demo.js:190`）；这一步需要补一条落盘线 |
| 4 | 整理进度（5 步真实状态）→ `纪要已生成` + 第一份纪要 | 点 `看纪要` / `展开全文` | 自动整理；`GET /api/soulmirror/record?dir=` | 没有“成功时刻”的引导：用户不知道这就完成了 |

### 6.2 现在缺的四步，怎么补（不新增依赖）

1. **首屏缺“试一次”入口。** 在状态 D 的 L1 放 `试一段录音`，直接调现有 `/demo`；不要把用户先赶到设置页。
2. **缺“配置清单”的首屏化。** 现有 `/setup` 已返回 `rows/hint/ok`（`index.js:1244`），`SetupCard` 也有逐项动作；把它的“只读摘要”提到状态 D 的 L2，按钮仍复用 `runSetup`。
3. **缺“演练 → 纪要”的落盘线。** 这是最容易被忽略的一处：`lib/demo.js:190` 只把句子追加到 `transcript.jsonl`，样例 PCM 没有写成 `audio.wav`，也没有调用会后整理。所以今天点完演练，只能证明“转写链路通”，不能产出纪要。补法二选一，均不新增依赖：
   - **推荐**：演练结束时把已经在内存里的样例 PCM 落成 `audio.wav`，然后调用现有 `/offline {dir}`，走同一套整段转写 → 纪要 → 知识库；这样演练和真实会议共用一条落盘/整理路径，不会出现“演练一套、真实一套”。
   - 备选：首次页直接提供“用示例录音生成纪要”，服务端把 `assets/demo_meeting.wav` 交给现有 `/import-recording`；代价是绕过一次“采集 → 落盘”，演示与真实的路径不完全一致。
4. **缺“成功后的交接”。** 第 4 步完成后，L1 文案从“演练完成”变成“下次开会会自动录音”，并给一个次级入口“打开会议软件”。这是从“试用”到“真实使用”的关键一跳，现在完全缺失。

> 顺带一处接线 bug：`live.set`（`client.js:170-191`）没有接 `j.demo`，所以 `SettingsSection` 里的“演练中”判断（`client.js:3009`）永远不成立，也拿不到 `demo.dir`。首次页要显示演练进度、把 `demo.dir` 交给 `/offline`，必须先把 `demo` 接进 `live`。

> 密钥的边界要说清：没有密钥，演练的**实时转写**可以先跑（`ScriptedTranscriber` 是离线脚本），但**整段转写/纪要**仍需要密钥或可用的本地离线识别。不要在首屏承诺“没有密钥也能出纪要”，也不要在失败时悄悄用演练稿冒充真实纪要。

### 6.3 边界

- 不自动入会；第 5 步只打开软件，不点加入。
- 不默认安装虚拟声卡；`vm` 项在设置里，标记“需要 UAC，本人点”。
- 不默认下载声纹模型；第 4 步之后再问“要不要让纪要认出人”，体积写在按钮上。
- 不新增依赖：`/demo`、`/auto`、`/offline`、`/record`、`/setup`、`/open` 都是现有接口。

### 8.4 不建议做的（避免过度设计）

1. **不要靠换主题色/加渐变解决“黑块”。** 黑块是“通栏 + token 可能解析成近黑 + 无图标”的层级问题；换皮只会把问题换个颜色。
2. **不要新增“简洁模式”或第三套 UI。** 现在已经是大页面 + 侧栏 + 字幕条 + 设置页；再加一套只会让“我该在哪操作”更难。
3. **不要把设置/诊断简单折叠就交差。** 先收敛问题（P1），再折叠；否则用户只是从“看见两条”变成“找不到两条”。
4. **不要做进度环/预计剩余时间/百分比。** 违反“无假进度”；整理步骤只显示真实阶段和真实字节。
5. **不要把声纹安装做成首次启动的强制引导。** 135MB 下载、模型选择、隐私同意都不该挡在“第一次看纪要”之前。
6. **不要删除四个 tab 的能力。** 运行轨迹、恢复、会议接入都是售后与审计入口；只降级，不删除。
7. **不要在客户端推导“当前会议/历史会议”。** 必须由 `view` 给出 `mode/meeting`；否则大页面和侧栏会出现两套状态。
8. **不要自动入会、自动预约、自动点“加入”。** 现有边界是对的。
9. **不要为了“商业感”加 hero 插画、品牌大图、装饰性渐变。** 会议面板的商业感来自“信息准确、下一步明确、少打扰”。

## 9. 验收清单（非设计师 3 分钟可核对）

1. **8 秒测试**：打开会议页，8 秒内能说出“现在在做什么、下一步点哪里”；不用滚动。
2. **一个主按钮**：首屏 filled 主按钮恰好 1 个；其余是 outline/文字/图标。
3. **完成态不出现录音主按钮**：`会后整理完成` 时，主按钮是 `看纪要`（或 `导出纪要`），不是 `立即开始录音`。
4. **诊断最多一条**：首屏红/黄条 ≤1 条；每条只有 1 个动作按钮；多出来的显示“还有 N 个问题”。
5. **正常状态不报警**：没开会、链路正常时，首屏没有红/黄块，只有一行灰字。
6. **人话检查**：首屏文字里搜不到 `devices.`、`captureAuto`、`apps`、`asr.`、`preflight`、`401`（这些只能在“查看原因/复制排查信息”里）。
7. **数字有主语**：时长显示为 `16 分 38 秒` 或 `12:35`；完成后不再出现持续增长的 `已用 N 秒`。
8. **一屏一对象**：首屏标题区能读到“今天 10:42 的会议 / 腾讯会议 · 第 12 分 35 秒”，不是目录名 `2026-11-12T...`。
9. **四态可切换**：进行中 → 结束后整理 → 完成 → 历史，每种状态只换 L1 与内容，不出现“完成 + 录音”这种矛盾组合。
10. **历史可筛选**：73 场里能一眼区分“有纪要 / 未整理 / 没音频”；默认先看到可整理/有纪要的。
11. **首次 5 步内出纪要**：密钥已由环境提供或第 1 步填好后，用演练跑通并拿到第一份纪要；第 4 步明确告诉用户“这就是完成”，第 5 步给“接真实会议”的入口。
12. **低频操作不占首屏**：删除空记录需要两次点击且在“更多/原因”里；导入、安装、重新整理、导出都不在首屏主位。
13. **420px 不横滚**：主按钮、标题、事实行在 420px 宽下不换行截断；长文本进 `details`。
14. **两个入口一致**：大页面与侧栏显示同一个 `headline`、同一个主按钮、同一条问题；不出现“侧栏说完成、大页面说等待”。
15. **token 兜底**：所有颜色都来自 `T`；`theme-fallback` 测试通过，且没有新增裸 `var(--dsw-*)`。

## 10. 一句话总结（给评审会用的版本）

> 现在的问题不是“元素太多”，而是**同一份状态被当成三种东西用**：标题、说明、按钮各说各的。
> 把 `view` 拆成“状态 / 这场会 / 下一步”三件事，首屏就只需要回答一个问题：
> **“现在这场会进行到哪，我下一步点哪里？”**
> 其余信息按“这场会议 → 认识的人 → 之前的会议”三层折叠，诊断收敛成一条，低频动作收进 `⋯`。
> 这样既保留“先落盘后展示、单一投影、无假进度”的底线，也能让第一次打开的人在三分钟内拿到一份纪要。
